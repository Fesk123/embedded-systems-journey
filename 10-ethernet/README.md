# Ethernet Networking — VirtIO Network Interface

## Overview

The Ethernet project introduces network connectivity to the custom RV64GC computer using the existing Gigabit Ethernet capabilities of the AMD Kria KV260 platform.

Instead of implementing a complete Ethernet MAC and PHY from scratch, this project uses a VirtIO-based network interface. The RV64GC processor communicates with the virtual network device through memory-mapped registers and transmit and receive queues. Software running on the KV260's Processing System (PS) acts as the backend and forwards network packets to the Linux networking stack through a TAP interface.

This approach separates the processor's network interface from the physical Ethernet hardware. It allows the RV64GC system to use the KV260's existing network connectivity without requiring a complete Ethernet controller implementation in the programmable logic (PL).

The long-term goal is to enable network access from the RV64GC computer, providing a foundation for Linux networking, remote communication, software downloads, and network-based applications.

## Project Goals

- Provide a VirtIO-based network interface for the RV64GC processor.
- Implement memory-mapped VirtIO registers.
- Support transmit and receive packet queues.
- Implement network-device interrupt signalling.
- Connect the PL network interface to the KV260's PS.
- Forward packets between the RV64GC system and the Linux networking stack.
- Use shared DDR memory for packet buffers where appropriate.
- Avoid unnecessary packet copying and excessive bus traffic.
- Verify device initialization, queue handling, and interrupts through simulation.
- Establish a foundation for network access from a future Linux system.

## Architecture

### 1. VirtIO Network Device ("eth_virtio_net.v")

The main module implements the hardware-side VirtIO network device.

Its responsibilities include:
- Connecting the RV64GC processor to the network device.
- Coordinating transmit and receive operations.
- Managing network-device state.
- Connecting the VirtIO register interface to the packet queues.
- Reporting device events and errors.

The module provides the network interface expected by compatible VirtIO network-device software.

### 2. VirtIO MMIO Interface ("eth_virtio_mmio.v")

This module implements the memory-mapped register interface used to configure and control the network device.

Its responsibilities include:
- Exposing device identification and configuration registers.
- Supporting device initialization and status updates.
- Handling feature negotiation.
- Providing access to queue configuration.
- Supporting notification of available transmit and receive work.
- Reporting device status and errors.

The MMIO interface allows software to discover and configure the device without requiring a dedicated physical Ethernet controller in the PL.

Correct compatibility with the VirtIO specification and the intended guest driver must be verified during integration.

### 3. Transmit Queue ("eth_tx_queue.v")

The transmit queue manages packets sent by the RV64GC system.

Its responsibilities include:
- Tracking available transmit buffers or descriptors.
- Identifying packets ready for transmission.
- Passing packet data to the PS-side backend.
- Updating queue state after processing.
- Handling queue availability and completion.

The queue must prevent packets from being processed more than once and ensure that descriptors are not reused before their operations are complete.

### 4. Receive Queue ("eth_rx_queue.v")

The receive queue manages packets arriving from the network.

Its responsibilities include:
- Tracking buffers available for incoming packets.
- Receiving packet data from the PS-side backend.
- Making completed packets available to the RV64GC system.
- Updating descriptor and queue state.
- Handling unavailable buffers and receive errors.

The guest software must provide suitable receive buffers before incoming packets can be delivered to the processor.

### 5. Interrupt Controller ("eth_irq.v")

This module handles interrupts generated by the network device.

Interrupts can notify the processor about events such as:
- Transmit queue completion.
- Receive queue activity.
- Device status changes.
- Relevant errors.

The interrupt interface must be integrated with the SoC's existing interrupt architecture. Full interrupt delivery depends on the corresponding CPU and interrupt-controller integration.

### 6. PS Bridge ("eth_ps_bridge.v")

The PS bridge connects the network device in the programmable logic to software running on the KV260's Processing System.

Its responsibilities include:
- Exchanging packet requests and completion information.
- Coordinating communication between the hardware queues and PS software.
- Managing the relevant control and data interfaces.
- Supporting the transfer of packet data through shared memory or another implemented data path.

The bridge must handle differences in timing and processing speed between the RV64GC subsystem and the PS-side backend.

### 7. PS Network Backend ("eth_ps_backend.c")

The software backend runs on the PS and connects the hardware-side VirtIO interface to the host's networking facilities.

The intended responsibilities include:
- Retrieving outgoing packets from the hardware-side interface.
- Forwarding packets to a Linux TAP interface.
- Reading incoming packets from TAP.
- Delivering received packets to the hardware-side interface.
- Reporting operation results and errors.
- Coordinating buffer ownership and queue completion.

The TAP interface provides a software-accessible network endpoint. Linux networking tools can then be used to configure the interface and provide connectivity through the host's network configuration.

Actual connectivity depends on the backend implementation, TAP configuration, network routing, and the available PS-to-PL interfaces.

## Packet Flow

### Transmit Path

1. The RV64GC software prepares a network packet.
2. The packet is made available through the VirtIO transmit queue.
3. The hardware-side interface identifies the pending packet.
4. The PS bridge makes the packet available to the backend.
5. The PS software forwards the packet to the TAP interface.
6. The Linux networking stack and host network configuration handle further transmission.

### Receive Path

1. A packet arrives through the host's networking facilities.
2. The PS backend reads the packet from TAP.
3. The packet is transferred to the hardware-side network interface.
4. The receive queue places the packet into an available receive buffer.
5. The device updates the queue state and signals an interrupt when appropriate.
6. The RV64GC software processes the received packet.

These flows describe the intended system architecture. End-to-end operation must be verified against the actual queue, bridge, backend, and data-transfer implementations.

## Shared DDR Memory and Performance

Network packets can be larger than the control information required to manage them. Transferring all packet data through MMIO registers would introduce unnecessary overhead.

Shared DDR memory is therefore an important part of the intended design.

Potential benefits include:
- Reduced copying between subsystems.
- Efficient handling of larger packets.
- Separation of control operations from bulk data transfers.
- Better throughput when handling multiple packets.

However, shared memory introduces several design requirements:
- Correct buffer addresses and packet lengths.
- Clear ownership of descriptors and packet buffers.
- Synchronization between the RV64GC processor and PS software.
- Correct ordering of memory operations.
- Cache maintenance or coherent access where required.
- Safe handling of buffer reuse and queue completion.

The exact performance depends on the implemented data path, memory-access mechanisms, queue design, and software backend.

## Main Challenges

### VirtIO Compatibility

The device must implement the register layout, status transitions, feature negotiation, queue configuration, and descriptor handling expected by the intended VirtIO driver.

A mismatch between the device implementation and software driver can prevent initialization or cause packet transfers to fail.

### Packet Buffer Management

Transmit and receive queues must maintain correct descriptor ownership and completion state. Incorrect handling can lead to dropped packets, duplicate packets, or memory corruption.

### Shared Memory and Cache Consistency

The RV64GC subsystem and PS software may access shared DDR buffers through different interfaces. Cache maintenance or a suitable coherent-memory mechanism is necessary when the interfaces do not automatically maintain consistency.

### Data-Transfer Bottlenecks

The PS bridge, bus interconnect, DDR access path, and software backend can all limit network throughput.

The design should avoid unnecessary copying and keep control-register traffic separate from bulk packet transfers.

### Interrupt Integration

Network events must be delivered correctly to the processor. This requires coordination between the device's interrupt logic, the SoC interrupt controller, and the CPU's interrupt-handling implementation.

### TAP and Linux Networking

A functional hardware device does not automatically provide Internet connectivity. The PS backend, TAP interface, IP configuration, routing, and any required host-side forwarding must also be configured correctly.

## Current Limitations

- The design uses a VirtIO network interface rather than implementing a complete Ethernet MAC and PHY in Verilog.
- The KV260's existing Gigabit Ethernet capability is accessed indirectly through the PS-side networking facilities.
- The PS backend must be implemented and integrated with the hardware bridge.
- Shared-memory packet transfer requires a correctly implemented data path.
- Cache consistency and buffer ownership must be handled explicitly where necessary.
- Full network connectivity depends on the VirtIO driver, PS software, and Linux networking configuration.
- FPGA hardware verification is required to establish end-to-end operation and measure actual performance.

## Future Improvements

Potential improvements include:
- More efficient packet-buffer management.
- Reduced packet copying.
- Improved queue scheduling.
- Better error reporting and recovery.
- Support for multiple outstanding packet operations.
- Performance measurements for transmit and receive throughput.
- Integration with the RV64GC Linux networking stack.
- Network-based software downloads and remote access.
- Further optimization of the PS-to-PL data path.

## What's Next

The next project is Graphics and Framebuffer Support.

The goal is to give the RV64GC computer the ability to generate graphical output, providing a foundation for a graphical Linux environment, applications, and simple games.

Planned features include:

- Framebuffer memory for storing pixel data.
- Configurable display resolution and pixel format.
- A graphics interface that allows the processor to write pixel data.
- Integration with the existing SoC memory and bus architecture.
- A display output path compatible with the available KV260 hardware interfaces.
- Support for basic graphical operations and test patterns.
- Simulation and verification of framebuffer access and pixel generation.
- Future integration with a Linux graphical environment.

The initial focus will be on implementing and verifying the framebuffer and graphics pipeline in simulation. Display output on the KV260 can then be tested using suitable hardware interfaces and display connections.
